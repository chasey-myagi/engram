本地架构主题如何影响选题

对 harness-pi：优先看 execution traces、typed outcomes、budget / resume、tool feedback、permission / safety boundary、replanning、trajectory-aware grading、multi-agent orchestration。
对 Engram：优先看多轮记忆构建、冲突/修订、evidence-linked grading、可回溯 provenance、usage / evaluation 回流，以及 memory 不只做 recall 而是参与后续 action。

1

Harness-Bench

Paper / Benchmark HF 发布 2026-05-27 高置信

主链接：HF Paper

辅助链接：arXiv · Project / GitHub / Leaderboard

摘要：专门测“同一任务环境里，不同 harness 配置带来的执行层差异”。论文把 agent 能力从“模型能力”拆成“model-harness pairing”，用 106 个 sandboxed offline tasks 和 5,194 条 execution trajectories 去量化 completion、效率、过程质量与 failure behavior。

为什么重要：这几乎就是 harness-pi 当前最缺的验证面。它把 context/tool/state/constraint/permission/tracing/recovery 当成 harness 一等公民，而不是默认固定。

证据：HF 页面给出任务数、轨迹数、shared budgets/protocol、execution-alignment failures 等核心结果；项目站点补了 GitHub/Leaderboard/Explore Tasks。

注意点：HF 页面本身尚未挂出 dataset/model/space 互引，开源资产还需要从项目站点继续跟；但对本轮“该不该深挖”的判断已经足够。

2

HarnessAudit / HarnessAudit-Bench

Paper / Benchmark / Task Browser arXiv 2026-05-14 高置信

主链接：Project

辅助链接：arXiv · HF Daily Papers query

摘要：这不是“最终答案安全性”评测，而是完整轨迹审计。站点公开了 210 tasks、8 domains、24 scenarios、69 role templates、10 harness configs，并把评测拆为 boundary compliance、execution fidelity、system stability 三层。

为什么重要：harness-pi 已经在谈 permissionGate、fail-closed、Event Bus、PostgresSessionStore；HarnessAudit 正好提供“工具权限、资源访问、角色间信息流”如何被系统性审计的外部参照。

证据：项目站点直接给 GitHub、HF、sample tasks、live data；关键发现里明确写出 best overall 仅 0.32，completion 与 safety 负相关，resource access 是主风险面。

注意点：它更偏 safety audit 而不是一般性 product benchmark；如果只关心 task completion，会低估它的价值。

3

ProofAgent Harness

Framework / Evaluation Harness arXiv 2026-05-22 高置信

主链接：Docs

辅助链接：arXiv · GitHub · PyPI

摘要：定位是“多回合对抗式 agent evaluation infrastructure”。它围绕 planner → conductor → multi-juror scoring → debate consensus → reporter 组织评估流程，强调对既有 agent loop 做轻适配，而不是重写 agent。

为什么重要：对 harness-pi 而言，它提供了一个很实际的问题意识：评测本身也需要 harness，而不是只需要 benchmark 题库。对 Engram，则是 turn-level audit 和 evidence-linked report 的外部参考。

证据：文档页给出 arXiv、源码、PyPI、5 行适配器示例、local judge 支持、FakeLLM 测试夹具，以及 Apache 2.0 开源声明。

注意点：它的主卖点是 adversarial evaluation，不是通用 benchmark 全景；如果你要的是标准公开排行榜，它不替代 Claw-Eval/Harness-Bench。

4

Claw-Eval

Paper / Dataset / Leaderboard HF 发布 2026-04-07 高置信

主链接：HF Paper

辅助链接：HF Dataset · Project · GitHub

摘要：300 个 human-verified tasks，9 个类别，2,159 条 rubric，三条证据通道（execution traces / audit logs / environment snapshots）做 trajectory-aware grading，明确把 Completion、Safety、Robustness 分开看。

为什么重要：这和 Engram 的“claim 不能脱离 provenance / verification”在方法论上高度同构；对 harness-pi 则是 run summary / event flow / trace capture 为什么不能只保 final answer 的直接论据。

证据：HF paper 页面给出 44% safety violations 与 13% robustness failures 被传统 opaque eval 漏掉；HF dataset 页面给出 MIT license、benchmark 标签、leaderboard 接入。

注意点：成本与工程复杂度比单纯题库 benchmark 高；适合拿来定义“生产前 gate”，不适合一开始就全量照搬。

5

General Agent Evaluation / Exgentic

Paper / Protocol / Leaderboard HF 发布 2026-02-26 高置信

主链接：HF Paper

辅助链接：Project · GitHub · HF Results

摘要：提出 Unified Protocol 与 Exgentic 评测框架，强调 general-purpose agent 不该因为 benchmark integration 细节吃暗亏；论文在 6 个环境里评 5 种 agent，实现了首个 Open General Agent Leaderboard。

为什么重要：它对 harness-pi 的启发不是“再做一个 leaderboard”，而是先定义 agent-benchmark integration contract。这个点和本地想做 reusable runtime foundation 的方向一致。

证据：HF paper 页直接列出 GitHub、Project、Open General Agent Leaderboard，并显示 results dataset 最近仍有更新。

注意点：它的目标是 general-agent fairness，不是 memory 专项 benchmark；如果只看记忆与 provenance，这项优先级会低于 memory 组条目。

6

MINTEval

Paper / Memory Benchmark HF 发布 2026-05-19 高置信

主链接：HF Paper

辅助链接：arXiv · GitHub

摘要：专打 memory interference。数据有 15.6k QA pairs，平均上下文 138.8k tokens，单实例最长 1.8M tokens，覆盖 state tracking、multi-turn dialogue、Wikipedia revisions、GitHub commits。论文给出的平均准确率只有 27.9%。

为什么重要：如果 Engram 想把“冲突、修订、旧事实被新事实覆盖”做成真命题，MINTEval 比只测 recall 的数据更接近真实痛点。

证据：HF paper 页面写明 retrieval 与 memory construction 是主瓶颈，作者评论区直接给出 code + dataset 仓库。

注意点：它是 benchmark，不是现成 memory runtime；想直接迁移工程实现会落空，应该学的是 failure taxonomy 与干预变量。

7

AMA-Bench

Paper / Dataset / Leaderboard HF 发布 2026-02-26 高置信

主链接：HF Paper

辅助链接：HF Dataset · Project · GitHub

摘要：把 long-horizon memory 重新放回 agent trajectories，而不是只盯人机对话。论文里 AMA-Agent 用 causality graph + tool-augmented retrieval，在 AMA-Bench 上达到 57.22%，比最强 baseline 高 11.16%。HF dataset 页面可直接看到 208 个 test rows、12 task types、6 domains、trajectory 最长 525 turns、token 可到 1.03M。

为什么重要：它很适合拿来校验 Engram 是否真的帮助“跨长轨迹的 objective retention / causal reconstruction”，而不是只让 recall 更像 RAG。

证据：HF paper 和 dataset 信息足够完整，license 为 MIT，且 GitHub/leaderboard 都挂全。

注意点：当前公开数据规模不大，更适合精测与 ablation，不适合直接拿它当大规模 pretraining 语料。

MemoryAgentBench

Paper / Dataset / GitHub HF 发布 2025-07-07 高置信

主链接：HF Paper

辅助链接：HF Dataset · GitHub

摘要：它把 memory agent 拆成四项核心能力：accurate retrieval、test-time learning、long-range understanding、conflict resolution。虽然不是本轮最新，但公开度高、GitHub 信号强，而且和“多轮记忆”主题高度贴合。

为什么重要：对 Engram 来说，它仍然是把 memory 评测从“长上下文问答”推进到“持续积累 + 更新 + 冲突处理”的早期关键基线。

证据：HF paper 页面直接挂 GitHub；作者在社区帖里对四项能力的定义和 benchmark 设计思路解释得很完整。

注意点：相较 2026 年的新 benchmark，它更像“成熟起点”而不是最新上限；本轮应把它视为基线参照，不是唯一方向。

PAC-BENCH

Dataset / Multi-Agent Benchmark HF 数据近期可访问 高置信

主链接：HF Dataset

辅助链接：arXiv

摘要：专测 privacy constraints 下的 multi-agent collaboration。HF dataset 卡片提供 3-stage pipeline：scenario generation、simulation、evaluation；可直接复现实验，也能用内置 100 scenarios 或扩展到 1,478 scenarios。

为什么重要：如果 harness-pi 后续要进入 multi-agent orchestration，PAC-BENCH 比一般协作 benchmark 更早触及“信息流边界、隐私抽象过度、privacy-induced hallucination”这些真实难点。

证据：arXiv 抽象明确指出 privacy constraints 显著拉低协作表现；HF dataset 页面给出分阶段运行方式、Conda 环境、scenario count 和 CC-BY-4.0 license。

注意点：HF 数据页存在 YAML metadata warning，说明仓库卡片打磨还不够细；但 benchmark 主体与可执行流程是完整的。

ReSearch-Qwen-7B-Instruct

Model / Research Agent 模型与代码开源 2025-03-26 中高置信

主链接：HF Model

辅助链接：arXiv · GitHub

摘要：这是本轮唯一进入 Top 10 的模型项。模型卡片写得很完整：MIT license，明确给出训练/评估流程、FlashRAG 检索服务、verl 训练基础、SGLang serving、以及 open-source models 发布节点。

为什么重要：它不是 memory/harness benchmark，但对“research agent 是否把 search 当成一等动作”很有参考意义。尤其是它把 search rollout、retriever serving、evaluation 环境拆得比较清楚，适合做 harness-pi 工具层/搜索层的设计对照。

证据：HF model 卡直接包含 installation、data prep、training、evaluation、paper、训练数据来源与版本信息。

注意点：它更接近 search-augmented reasoner，不是通用 harness。把它放进榜单是为了覆盖“可复现实验的模型资产”，不是因为它能直接解决 runtime 设计问题。

Deep Dive

首选深挖：Harness-Bench

如果只允许今天带走一个最值得本地复用的对象，我会选 Harness-Bench。原因不是它“最热”，而是它最直接命中 harness-pi 正在构建的那一层：执行栈，而不是单一模型。

对本地最关键的一点不是 benchmark 分数，而是它明确主张：agent capability 应当按 model-harness configuration 报告，而不是被粗暴地归因给 base model。

证据来源：HF paper 摘要与 arXiv abstract

它是什么

一个专门测 harness effect 的 diagnostic benchmark。不是把完整 agent system 黑箱对打，也不是固定 harness 只测模型，而是在共享 tasks、budgets、protocol 下比较不同 harness 配置的执行表现。

核心结构

106 个 sandboxed offline tasks，覆盖 realistic workflow；每次运行都会记录 final artifacts、execution traces、usage stats、validator outputs。也就是说，它默认“过程数据”与“最终答案”同等重要。

为什么比普通 agent benchmark 更贴近本地

本地不缺“模型能答题吗”的问题，缺的是 SessionStore / Event Bus / permission / recovery / trace / evidence contracts 这些 runtime decisions 会不会改变最终行为。Harness-Bench 正是拿这一层开刀。

实现/设计亮点

把 harness 定义为执行层系统：context、tools、state、constraints、permissions、tracing、recovery 都在定义内。这和 harness-pi docs/09 里对 kernel/plugin/controller/adapter 分层的焦点高度一致。
不抹平原生执行行为：它强调在 shared protocol 下“保留各 harness 的 native execution behavior”。这点很关键，因为真正影响执行可靠性的恰恰是行为差异，而不是被 benchmark adaptor 统一之后的平均形态。
输出可审计过程物：final artifacts + traces + validator outputs 让失败可以被切层诊断。这和 Engram 的 raw source → claim → page 思路相通：不要只看最后结论，要保中间可钻回证据。

评测/结果层面最值得吸收的点

规模够说明问题：5,194 条 trajectories 已经不是玩具量，足够显示 completion、efficiency、failure behavior 会随 harness 配置显著变化。
失败模式不是“模型笨”而是 execution misalignment：论文明确提到 reasoning 会和 tool feedback、workspace state、evidence、verifiable output contract 脱钩。这正是 runtime 设计该抓的病灶。
报告粒度正确：它要求按 model-harness pairing 报告能力。这比“某模型在某 agent 上 42%”更诚实，也更适合本地做 block-by-block hardening。

源质量判断

证据

HF paper 页面信息完整，arXiv 可直接访问，项目站点已提供 GitHub / Leaderboard / Explore Tasks。即使 HF 还没有 dataset/model 互引，这个项目也已经超过“只发论文、无资产”的阈值。

推断

从站点结构看，它明显在走“benchmark + live leaderboard + task browser”路线，而不是一次性论文发布后冻结；因此更值得后续跟踪，而不是只摘一句 abstract。

它对 harness-pi 的映射

Event Bus / traces：Harness-Bench 默认把 execution traces 当必需品，本地应继续把 onPostToolUse、turn 边界、resume、abort、validator 输出汇成稳定事件面，而不是仅做日志旁路。
TerminalResult / validator contracts：既然 benchmark 要看 verifiable output contract，harness-pi 的 typed terminal outcomes 不应只表示结束原因，还应给外层 validator / scorer 可消费的稳定摘要面。
SessionStore / replay：如果未来要做 Harness-Bench 类实验，本地必须保证 resume 和 transcript 物化稳定，否则“同一 harness 配置”的比较就会混入观测误差。
permission / recovery is part of capability：本地不该再把 permissionGate、restart、budget overflow 视为周边机制；它们本身就是执行能力的一部分。

它对 Engram 的映射

evidence-linked evaluation：Harness-Bench 的 validator / trace 思路适合映射到 Engram 的 report_usage 与 claim_verification，把“这次 agent 为何采信/误信”沉成可追责事件，而不只是分数。
claim 级可归因失败：Engram 需要的不只是 recall 指标，而是“哪条 claim、哪次使用、哪类 evidence contract 断了”。Harness-Bench 的执行对齐视角对这里很有帮助。
校准不应脱离运行时：如果 completion、process quality、failure behavior 都受 harness 影响，那么 Engram 的 confidence / calibration 也不应被当作与 harness 无关的静态函数。

局限与风险

对 memory / provenance 本身不是主攻方向：它主要回答 execution-layer variation，而不是长期记忆系统应该如何建模。
可能更偏离线 sandbox：如果本地未来更重真实 web/live system 交互，还需要和 REAL、Claw-Eval 这类资产组合使用。
HF 互引生态还没成型：目前 HF 页面没有 dataset/model/space 互引，说明生态挂接还早期；对“持续维护成熟度”要保留一点审慎。
结论：如果只选一个本地后续动作，不是“立刻复刻 Harness-Bench 全套”，而是先把 harness-pi 的执行事件、validator 输出、run summary、resume 语义整理成可被 Harness-Bench 类工作消费的稳定接口。等接口稳了，再决定是接它，还是自己做更贴近 coding/workspace 的评测面。
Next Steps

对本地的具体后续建议

下面三组动作按收益/代价排序。它们都尽量贴近已有架构，而不是另起一套“研究用旁路系统”。

1. 先补执行证据面

给 harness-pi 明确一个可导出的 trace contract：turn start/end、tool call/result、abort、resume、validator、usage。目标不是“日志更漂亮”，而是让 Claw-Eval / Harness-Bench 那类 trajectory-aware 评测在本地有挂点。

2. 用 memory benchmark 反推 Engram eval

优先吸收 MINTEval + AMA-Bench + MemoryAgentBench 的 failure taxonomy，把 recall / revision / interference / conflict resolution 分开记。不要把所有 memory failure 混成一个 accuracy。

3. 多 agent 时先拿 PAC-BENCH 对边界做压测

如果 harness-pi 进入 multi-agent orchestration，先把 PAC-BENCH 风格的 privacy / role boundary 当红线，而不是等功能做成后再补安全评测。

4. 对模型资产保持克制

本轮只有 ReSearch-Qwen-7B-Instruct 作为模型项过线，原因是它的 model card 足够完整。其余 HF 上大量“agentic / memory / research”模型仍停留在弱卡片、低下载或无清晰评测资产，不值得今天纳入主结论。
