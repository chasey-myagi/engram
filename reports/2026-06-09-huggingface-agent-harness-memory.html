Overview

筛选方法与本地对照

我怎么筛

  • 发现阶段只用 Hugging Face 站内页面、HF Daily Papers、HF dataset / space / docs 页面做初筛。
  • 只有候选进入 shortlist 后，才补查 GitHub、arXiv、Papers with Code 或项目站点，确认 license、更新时间、代码/数据是否能拿到、有没有可重复运行说明。
  • 这次我主动压掉了几类低信号：无 license、只有聚合页没有具体 artifact、Space 像 hackathon demo 但缺 benchmark 或 repo、以及过旧且最近没有维护迹象的经典项目。

本地架构为何影响选题

  • 对 harness-pi：我优先看能映射到 controller / sub-agent / summary / event / persistence contract 的资产。
  • 对 Engram：我优先看 claim-level factuality、citation / provenance、memory read-write loop、以及评测是否能跟真实消费闭环。
  • 证据与推断分开：报告里的“摘要 / 结果 / 指标”是源页面证据；“为什么重要 / 如何映射本地”是我的工程推断。
本轮没把任何“只靠热度上榜”的资产写进主榜。像 DeepResearch-9K 这类条目虽然新，但 HF 数据集卡片缺 license；像较早的 open_Deep-Research 虽然历史意义大，但时间上已不算这轮“最新一批”。
Top 10

Top 10 高置信发现

smolagents

框架 高置信
HF 主页 文档 GitHub Actions Releases

近期信号：HF 名下相关 dataset 最近还能看到 2026-04-20 更新；GitHub Actions 页面最近一周仍有 v1.27.0.dev0 相关活动，release 页面可见较新的稳定版本链。

摘要：这是 Hugging Face 当前最清晰的 agent framework 资产：CodeAgent / ToolCallingAgent 两条范式并存，强调代码型行动、工具组合与沙箱执行；HF 命名空间下还挂着 traces、benchmark 数据和 GUI/浏览相关训练数据。

为什么重要：如果只看“runtime 最小原语 + 可实验性”，它对 harness-pi 很有对照价值，尤其适合拿来比较“代码型动作”与“结构化工具调用”的边界。

注意点：它是 Python-first 的 agent library，不自带 Engram 那种 append-only provenance、claim ledger 或统一评测闭环。

DR3-Eval

数据集 / benchmark 高置信
HF Dataset HF Paper GitHub

近期信号：HF 数据集创建于 2026-03-11，最近修改 2026-04-20，Apache-2.0；GitHub README 给出完整 quickstart、batch 与 eval 命令。

摘要：面向 deep research agent 的多文件、多模态、可复现 benchmark。核心做法是：真实用户文件、反向构造 query、每题独立静态 sandbox corpus、再用 IR / CC / FA / IF / DQ 五维评估生成报告。

为什么重要：这是本轮对 harness-pi 与 Engram 的交集命中率最高的条目：它既有分层子代理结构，也有 citation coverage / factual accuracy 这种 Engram 能直接吸收的评测维度。

注意点：公开任务数仍只有 100；reference agent 基于 MiroFlow，外推到别的 runtime 时要小心别把框架偏好当方法论本身。

AEC-Bench

paper / benchmark 高置信
HF Paper GitHub

近期信号：HF 论文页发布时间 2026-03-31；GitHub 组织页显示 repo 于 2026-04-15 更新，Apache-2.0，且明确对外释放 benchmark dataset、agent harness 与 evaluation code。

摘要：一个多模态 AEC 领域 benchmark，覆盖 drawing understanding、cross-sheet reasoning 与 construction coordination。最关键的是它不是只报模型分，而是比较“同一基础 harness 上哪些 tool / harness design 技巧能稳定增益”。

为什么重要：这很接近本地真实问题：不是单纯换底模，而是问“编排、工具、流程设计到底值多少分”。

注意点：领域约束很重，任务形态跟通用 coding / knowledge agent 仍有距离，迁移时应抽象出 harness-level 结论而不是照搬 AEC task。

DeepFact

paper / factuality 中高置信
HF Paper arXiv

近期信号：HF 论文页发布时间 2026-03-06，最近一个月仍在 HF Daily Papers 检索中被频繁引用。

摘要：这是面向 deep research report factuality 的共演化基准：作者先证明静态专家标注本身在隐藏 micro-gold 上只有 60.8%，再引入 Audit-then-Score 机制，让 verifier 提交证据、auditor 审核、被接受的修订反过来更新 benchmark；四轮后专家一致性提升到 90.9%。

为什么重要：对 Engram 尤其重要，因为它把“版本化 benchmark + 审计证据 + 评测反哺标签”说得非常清楚，几乎就是 claim-level factuality 的评测治理层。

注意点：我在本轮没有从 HF 页面直接确认公开代码/数据仓库，因此它更像高价值方法论文，而不是已经完全可拿来跑的开箱资产。

K-BrowseComp

paper / dataset 高置信
HF Paper HF Dataset

近期信号：HF 论文页发布时间 2026-06-01；HF 数据集创建同日、最近修改 2026-06-02，MIT license。

摘要：韩语网页浏览 agent 基准，含 400 题，其中 300 题由母语者手工构造与验证。HF 页面给出的结果相当克制：在 verified split 上，frontier 模型也只到 30.00%–45.67%，合成诊断 split 更低。

为什么重要：它提醒一件事：browser agent 的“会不会搜”与“会不会在跨语言真实网页环境里找对证据”不是一回事。对任何想做国际化 research agent 的 runtime 都是硬压测。

注意点：场景非常韩语语境化，若只做中英文工作流，价值更多在方法压力测试而非直接复用题目。

EvoMemBench

paper / memory benchmark 中高置信
HF Paper arXiv GitHub

近期信号：HF 论文页发布时间 2026-05-18，代码仓库由论文直接给出。

摘要：它把 agent memory 拆成两个轴：memory scope（episode 内 / 跨 episode）与 content（knowledge-oriented / execution-oriented），并在统一协议下比较 15 种 memory 方法与长上下文 baseline。结论不讨巧但很有价值：长上下文仍很能打，没有一种 memory 形式在所有场景里都赢。

为什么重要：它能防止本地 memory 讨论失真。对 Engram 来说，claim/retrieval memory 不是万能药；对 harness-pi 来说，execution-oriented memory 可能更像程序化经验而不是知识库。

注意点：我没有在本轮额外核对该 repo 的 license 与近期维护强度，因此“可重复跑”的信心略低于 DR3-Eval 这类直接可见 setup 的项目。

MemOS

paper / project 高置信
HF Paper GitHub Project

近期信号：HF 论文页虽然是 2025-07-04，但 GitHub 页面在最近一月仍可见 release / issue 活动，且 repo 量级已经到 1,788 commits、9.62k stars、853 forks。

摘要：它把 memory 当作系统资源来做，核心抽象是 MemCube，统一纯文本、activation、参数级三层 memory，并加 scheduler、预加载、self-hosted / cloud 双形态与独立 evaluation 目录。

为什么重要：如果想看“agent memory 被真正系统工程化以后会长成什么样”，它是本轮最成熟的样本，不只是论文概念。

注意点：它覆盖面非常大，也带来更高的抽象与集成成本；对 Engram 这种强调 provenance 与 claim 审计的内核来说，并不是一比一兼容的答案。

Terminal-Bench 2.0

paper / benchmark 高置信
HF Paper Project Site

近期信号：HF 论文页发布时间 2026-01-17；项目站点最近三周仍显示 89 个 active tasks。

摘要：用真实 CLI 任务、人工编写解法和完备测试去压 agent，而不是玩 toy shell task。HF 页面摘要明确写出：frontier 模型与 agent 在这个基准上仍低于 65%。

为什么重要：对 harness-pi 几乎是天然相关，因为它测试的就是长链工具调用、环境状态变化、失败恢复与验证闭环。

注意点：它是 terminal-native benchmark，memory / provenance 本身不是内建对象，需要你在运行时或评测层自己补。

MMBench-GUI

paper / dataset 高置信
HF Paper HF Dataset GitHub

近期信号：HF 数据集创建于 2025-06-25，最近修改 2025-08-15，Apache-2.0；GitHub 组织页与论文均指向公开 benchmark 代码与环境。

摘要：GUI agent 的分层 benchmark，跨 Windows / macOS / Linux / iOS / Android / Web 六个平台，分成内容理解、元素定位、任务自动化与协作四层，并额外提出 EQA 这种效率-质量联合指标。

为什么重要：如果你不想让 GUI benchmark 永远只有 pass / fail，这套分层 + 效率指标非常值得借鉴，也能和 EventPump / run summary 之类的本地统计面形成呼应。

注意点：相较 2026 年的新条目，它已不算最新；并且它更偏 computer-use 代理，不直接触达 Engram 那类 claim-centric memory。

Crafter

paper / multi-agent harness 中高置信
HF Paper arXiv GitHub

近期信号：HF 论文页发布时间 2026-05-28，并拿到 HF Paper of the Day；外部仓库统计显示 repo 创建与最近提交都在过去一周内。

摘要：一个非常“harness 取胜而不是 backbone 取胜”的案例：它把科学图形生成拆成多 agent harness，并联动 CraftEditor 与 CraftBench，处理不同 figure type、不同输入条件与可编辑 SVG 输出。

为什么重要：虽然任务域不在 research agent，但它是本轮最好的结构性证据之一：当对象是强结构化产物时，模块化 harness 往往比单纯换大模型更有效。

注意点：仓库太新，成熟度与社区复现仍待观察；它对本地的价值主要是“模块化编排模式”，不是任务本身。

Deep Dive

首选深挖：DR3-Eval

最佳本地重叠候选 2026 春季新面 Apache-2.0 数据集

如果只选一个本轮最值得本地跟进的候选，我会选 DR3-Eval，而不是更热的 memory 叙事或更炫的多 agent demo。原因很简单：它同时踩中了 harness-pi 的 runtime/orchestration 问题和 Engram 的 provenance/factuality/eval 闭环问题。

它是什么

一个面向 deep research agents 的现实型 benchmark。公开信息显示，它不是只给一个 query 和网页搜索，而是把“用户上传的多文件资料 + 独立静态 research sandbox + 报告生成 + 多维打分”做成一体。

为什么它比一般 research benchmark 更接近本地

因为它把 多文件输入、citation coverage、factual accuracy、静态可复现语料、子代理分工 放进了同一个协议里，而这些刚好对应本地最想做实的几根主梁。

核心结构

GitHub README 里最有意思的不是分数，而是 reference architecture：主代理维护全局任务上下文并跑 Plan-Execute-Observe，RAG search sub-agent 迭代检索 sandbox，file reading sub-agent 专门读长文件。子代理不共享全局状态，只返回高度压缩的 summary。

评测设计

它把报告评成五维：IR、CC、FA、IF、DQ。这比“最后答对没”更细，而且 CC 与 FA 分离尤其关键，正好避免“引用很多但内容不真”与“内容看似对但无出处”混成一个分。

结果层面的关键信号

公开 README 里给了几个很值钱的结论：最好模型在 512k 设置下也只有 65.6 平均分；上下文更长反而会被噪声拖垮；instruction following 和 factual accuracy 不是一回事；long-context 与 RAG 的优劣要靠 task 结构来分。

对 harness-pi 的映射

  • 子代理边界：它的“子代理不共享全局状态，只回 summary”与本地 subAgentTool、compactSummarize、controller 层 orchestration 思路高度相容。
  • 持久化与回放：静态 sandbox + batch eval 很适合拿本地 append-only SessionStore、RunSummary 与 EventPump 做完整轨迹记录。
  • bounded workflow：主 agent / search agent / file reader 其实正好可以落成受预算约束的 parallel() / pipeline() / controller 组合，而不是单一神代理。

对 Engram 的映射

  • raw source 对齐：用户文件与 sandbox 文档天然就是 Engram 的 source 层候选。
  • provenance 对齐：Citation Coverage 可以直接转成“claim 是否带足够 provenance”的可观测信号。
  • truth loop 对齐：Factual Accuracy 与失败类型完全可以通过 report_usage 风格事件回灌到评测和校准层。
  • L5 / gap 任务启发：静态 sandbox 里的噪声与缺证据设计，很适合演化成 Engram 的“该说不知道时说不知道”缺口题。

局限与风险

  • 任务量还不大，100 题更适合方法方向判断，不足以证明长期泛化。
  • reference agent 带有 MiroFlow 与特定 embedding 选择，不能把实现细节误当 benchmark 公理。
  • 它重在报告级评测，claim-level verification 仍可继续往下拆，这正是 Engram 可补的一层。

最该吸收的三个想法

  • reverse construction：先有证据，再反向构任务，减少评测歧义。
  • summary-only subagent contract：默认不共享大上下文，逼 runtime 做压缩与边界控制。
  • 把 citation 与 truth 分开：这对任何知识代理都比单一“答得好不好”更有诊断价值。
Recommendations

对本地的具体后续建议

1. 先做一个最小 DR3-style eval slice

不要一下子复制 DR3-Eval 全套。先取 5 到 10 个多文件任务，做一个 main agent + file-reader + retrieval agent 的最小 slice，要求每个子代理只回 schema 化 summary，并把 RunSummary、tool 调用、引用对象都持久化。

2. 把 citation 与 factuality 分成两张表

Engram 这边不要把“有出处”与“内容为真”混成一个指标。至少拆成 CC-like 与 FA-like 两个面，分别记 provenance 充足度与 claim-level correctness。

3. 对 memory 叙事保持克制

从 EvoMemBench 与 MemOS 的对照看，knowledge memory、execution memory、long-context 替代关系远没有定型。对外表达时应避免把 Engram 说成“通用 agent memory 的全部答案”，而要明确它更像可审计 facts / provenance kernel。

4. 后续追踪优先级

如果明天继续扫，我会优先盯三条线：DR3-Eval / DeepFact 这类 deep research factuality 与 citation 基准、EvoMemBench 一类 memory benchmark、以及 AEC-Bench / Terminal-Bench 这类把 harness 价值显式量化的 benchmark。
